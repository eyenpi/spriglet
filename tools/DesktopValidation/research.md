# Desktop reliability review

The historical phase 3 review on 13 September 2026 used current Apple documentation and the installed Xcode 26.6 / macOS 26.5 SDK. It covered `PetInteractionView`, `PetWindowController`, the procedural `PetRenderView`/`PrototypePetScene`, and phase 1/2 validation records. The procedural renderer and its lifecycle harness have since been retired; the rendered-character migration is described below. Historical results remain available and do not certify the replacement renderer, physical cross-app input, or GPU performance.

## Transparent input routing

**Apple documents native transparent-window mouse-down routing.** `NSWindow.windowNumber(at:belowWindowWithWindowNumber:)` uses the same rules as mouse-down hit testing, omits windows that are transparent at the specified point or ignore mouse events, and may return a window belonging to another application. This is stronger evidence than the existence of a clear scene or a view hit-test override. It does not specify an alpha threshold or guarantee the actual pixels produced by a particular renderer. [Window-number query](https://developer.apple.com/documentation/appkit/nswindow/windownumber(at:belowwindowwithwindownumber:))

`NSView.hitTest(_:)` selects a descendant within a view hierarchy. The supplied point is in the view's **superview** coordinate system; the current interaction wrapper converts it correctly before testing the rendered shape. Returning `nil` outside a path does not itself redirect an event to a different process. `NSWindow.ignoresMouseEvents` separately makes the whole window transparent to mouse events. [View hit testing](https://developer.apple.com/documentation/appkit/nsview/hittest(_:)), [whole-window mouse transparency](https://developer.apple.com/documentation/appkit/nswindow/ignoresmouseevents)

The phase 3 source made the panel nonopaque with a clear background, disabled its native shadow, enabled `SKView.allowsTransparency`, and cleared the scene. That procedural renderer used `.aspectFill` to avoid its fitted side bars. Those were source-level transparency settings. Actual light/dark host observations remain necessary; the earlier texture export only proves that isolated scene image's alpha. Apple's transparent-scene guide includes a UIKit `UIView.backgroundColor` step; that last property is not an AppKit `NSView` API. [SpriteKit transparency](https://developer.apple.com/documentation/spritekit/creating-a-scene-with-a-transparent-background), [window opacity](https://developer.apple.com/documentation/appkit/nswindow/isopaque)

**Historical boundary risk:** the procedural scene painted a ground shadow with alpha 0.12, while `containsPet` excluded it. The painted shape's antialiasing can also extend outside its mathematical path. If native window hit testing selects one of those painted pixels, a later local `nil` hit cannot be assumed to pass it onward. The fixture therefore tests clear corners, the outline, and the shadow independently. Physical input at these boundaries remains unverified.

The window-number API predicts **mouse-down** routing. Scroll behavior needs its own received-event checks. Apple documents that momentum scroll events can remain attached to the view where the flick began. The fixture reads the preferred `scrollingDeltaX/Y` properties and identifies precise versus coarse units instead of treating every event as a new gesture. [Scroll delivery](https://developer.apple.com/documentation/appkit/nsresponder/scrollwheel(with:)), [momentum receiver](https://developer.apple.com/documentation/appkit/nsevent/momentumphase), [preferred scroll delta](https://developer.apple.com/documentation/appkit/nsevent/scrollingdeltay)

## Activation, focus, and cancellation

`.nonactivatingPanel` is the current style-mask case for a panel that does not activate its owning app. Nonactivation alone does not mean a panel cannot take keyboard focus. Apple's `becomesKeyOnlyIfNeeded` documentation connects a nonactivating panel's key behavior to the hit view's `needsPanelToBecomeKey`. Spriglet additionally makes `canBecomeKey` and `canBecomeMain` false, and its hit view declines first-responder/key-panel status. This supports a mouse-only desktop companion; it requires separate controls for keyboard entry. [Panel style](https://developer.apple.com/documentation/appkit/nswindow/stylemask-swift.struct/nonactivatingpanel), [conditional key behavior](https://developer.apple.com/documentation/appkit/nspanel/becomeskeyonlyifneeded), [view keyboard requirements](https://developer.apple.com/documentation/appkit/nsview/needspaneltobecomekey)

Apple uses the term “click-through” in `acceptsFirstMouse(for:)` to describe accepting the first click in an **inactive window**. That is distinct from passing a click through a transparent window to another app. The fixture's targets and buttons explicitly accept that first event, which removes an inactive control's default refusal as a confounding factor. Spriglet's interaction wrapper also returns true. [First-mouse behavior](https://developer.apple.com/documentation/appkit/nsview/acceptsfirstmouse(for:))

The macOS 26 SDK adds `NSResponder.mouseCancelled(with:)`. The interaction wrapper now overrides it and calls `cancelInteraction()`. Direct constructed-event checks verify that a cancellation clears a press/drag and that a late mouse-up produces neither a click nor a committed drag. Apple's method page does not describe all delivery conditions, so no particular operating-system cancellation scenario is claimed as reproduced. [Cancellation callback](https://developer.apple.com/documentation/appkit/nsresponder/mousecancelled(with:)), [constructing a local mouse-event object](https://developer.apple.com/documentation/appkit/nsevent/mouseevent(with:location:modifierflags:timestamp:windownumber:context:eventnumber:clickcount:pressure:))

The fixture uses the current `NSApplication.activate()` API for its own explicit launch, plus app/window delegate callbacks to count focus changes. It never activates Spriglet. App-targeted automation can change focus independently of the tested click; visible focus totals make that influence reviewable, but do not turn the result into a physical hardware test. [Current activation API](https://developer.apple.com/documentation/appkit/nsapplication/activate())

## Historical SpriteKit resources and paused startup

`SKView.isPaused` fixes the scene onscreen and stops actions and physics. Returning false from `view(_:shouldRenderAtTime:)` skips that target update/render. Spriglet additionally pauses the view after its finite clip settles, avoiding a continuing render-delegate loop. The phase 2 probe's stopped scene/render counters support that narrow observation; they do not count GPU presentations or WindowServer activity. [Pause contract](https://developer.apple.com/documentation/spritekit/skview/ispaused), [render decision](https://developer.apple.com/documentation/spritekit/skviewdelegate/view(_:shouldrenderattime:))

**Phase 3 fixed source defect:** a saved visible pause could be applied before the first SpriteKit frame, leaving a new pet invisible until resume. The phase 3 `PetRenderView` began paused and observed its attached window's occlusion changes. It allowed one initial neutral frame when a never-rendered host became visible, even if animation remained suspended, and then paused before another scene update. Hidden hosts did not warm a loop. Pausing an already-rendered pet remained immediate; active/queued clips were canceled and neutral was applied on resume. The allowance recorded a delegate decision, while the separate scene counter exposed a failed initial update.

That renderer observation used Foundation's macOS 26 `MainActorMessage` bridge for `NSWindow.didChangeOcclusionStateNotification`. The current website names a native AppKit typed message, but that symbol is absent from this installed SDK's AppKit Swift interfaces, so the existing public notification is bridged. That observation was removed when the view changed windows and at deinitialization. Apple documents the notification as a change in occlusion **state**, not every change to the occlusion region. The installed header also cautions that a nonrectangular or fully transparent window can still count as visible. Consequently visibility is a scheduling signal, not evidence that a pet pixel appeared. [Occlusion notification](https://developer.apple.com/documentation/appkit/nswindow/didchangeocclusionstatenotification), [occlusion state](https://developer.apple.com/documentation/appkit/nswindow/occlusionstate-swift.property)

Apple also documents automatic SpriteKit pausing when an app changes from active to inactive. The previous probes began and ended phases with the accessory app inactive; those boundaries do not exhaust every active-to-inactive transition. That limitation required a separate clip-started-while-active check. The new renderer uses its explicit app lifecycle policy rather than SpriteKit's automatic pause behavior.

Pausing or hiding is not a promise to release graphics memory. For the bitmap approach considered at that time, Apple explicitly says loaded `SKTexture` hardware memory stays until its referencing `SKTexture` is released, including references held by sprites and atlases. That contract neither diagnoses the procedural prototype's transient footprint increase nor describes the current CGImage buffer. Allocations and an exact-PID Release Metal/System trace are still required to explain growth or continuing GPU/compositor work. [Texture lifetime](https://developer.apple.com/documentation/spritekit/sktexture), [Metal performance analysis](https://developer.apple.com/documentation/xcode/analyzing-the-performance-of-your-metal-app)

## Rendered character migration

The current character uses decoded Blender PNGs in a child `CALayer`, with one `NSView.displayLink(target:selector:)` selecting a frame and its authored root displacement. The callback applies the window offset and image selection together; it does not prove atomic WindowServer/GPU presentation. A held frame holds its movement, and an underrun also freezes authored time. The layer retains a still image when the display link is invalidated, so a cold paused launch no longer needs a SpriteKit warm-up frame. [View display link](https://developer.apple.com/documentation/appkit/nsview/displaylink(target:selector:)), [layer contents](https://developer.apple.com/documentation/quartzcore/calayer/contents)

Image I/O decoding runs off the main actor through Swift's `@concurrent` function, using `kCGImageSourceShouldCacheImmediately`. The frame buffer is bounded; static rest and nap images are retained separately. `submittedFrameCount` counts image assignments and `displayLinkCallbackCount` counts the app's clock callbacks. They are distinct from the historical scene/delegate counters and from hardware presentations. [Immediate image decoding](https://developer.apple.com/documentation/imageio/kcgimagesourceshouldcacheimmediately), [Swift concurrency](https://www.swift.org/blog/swift-6.2-released/)

Local pet hit testing now uses a 64-pixel alpha mask with a solid-body threshold of 224/255. This keeps sampled semitransparent shadow pixels out of the local drag target; it does not specify WindowServer's alpha threshold or redirect cross-app input. Final exported PNG alpha and native light/dark compositing require their own checks.

The old `RendererLifecycleCheck.swift` executable source was retired. `build-lifecycle-check.sh` prints a migration message and forwards to the new build-only script. [CharacterSampleValidation](../CharacterSampleValidation/README.md) owns current asset, image/offset, interruption, alpha, and stopped-work checks. The independent desktop background/input fixture remains available above, and the phase 3 JSON files below are preserved as historical evidence.

## Scope of retained checks

At the phase 3 checkpoint, both fixture executables compiled with Swift 6 complete concurrency and warnings as errors. The procedural renderer also independently typechecked. The [headless lifecycle run](../../docs/results/phase-3/renderer-headless.json) passed **4/4 checks**: cancelled press cleanup, cancelled drag cleanup, hidden paused initial update count zero, and unchanged scene/render counters across a 500 ms interval.

The [native visible lifecycle run](../../docs/results/phase-3/renderer-lifecycle.json) passed **12/12 checks**, including those four cases. Cold visible paused and previously hidden paused hosts each received one initial scene update, then settled without further callbacks. An active reaction was interrupted by pause; resuming produced a neutral static update without restarting its action. App activity was false in the retained snapshots. These assertions cover native own-app windows and renderer state, not GPU output or physical cross-app input.

Separate [app UI observations](../../docs/results/phase-3/ui-observations.json) confirmed the visible still pet on a cold paused launch, directional placement/relaunch, restoration after cancelling a moving diagnostic, saved choices after quitting during the repeated check, and restored flags/home after cancelling the repeated check on Release. The background fixture received a calibration mouse-down, but an independent window-stack prediction differed; app-targeted automation may affect activation/order. The nonactivating pet could be inspected, while the automation drag request returned `noWindowsAvailable`. Consequently the physical drag, first-click, outline/shadow, scroll, and focus gates remain open.

The fixture disables window restoration and restoration snapshots, saves no test text or counters, and observes only its own events. [Disable restoration snapshots](https://developer.apple.com/documentation/appkit/nswindow/disablesnapshotrestoration()), [text editing delegate](https://developer.apple.com/documentation/appkit/nscontroltexteditingdelegate/controltextdidchange(_:))
