## Core contracts

`ActivityPolicy` holds independent suspension causes: `userPaused`, `hidden`, `occluded`, `systemAsleep`, `displayAsleep`, `sessionInactive`, and `thermalPressure`. Animation is eligible only when the set is empty. Clearing display sleep therefore cannot clear system sleep or an explicit pause; becoming unoccluded cannot override hidden state. The value type starts no timer, animation, or resume action. The app must separately remember whether the user requested an animation; eligibility becoming true must not invent a new action.

`PetPlacement` accepts global macOS screen coordinates and the current visible frame. The default margin is 12 points; resting placement is bottom-right. Margins shrink independently when a screen is too small to fit both margins. An oversized window is centered on the axis that cannot fit because full containment is mathematically impossible. Inputs must be finite with nonnegative dimensions and margin. Use the current `NSScreen.visibleFrame` when placing or reconfiguring the pet: Apple says it reflects the Dock, menu bar, and current display settings, and should not be cached. [Visible frame](https://developer.apple.com/documentation/appkit/nsscreen/visibleframe)

## Measure rendering and resource use

Use a Release build launched without the debugger. Record a 30-second warm-up, followed by separate 60-second intervals for static-visible, explicitly animating, manually paused, and hidden. Keep the desktop workload, refresh rate, power source, and app scale the same. Close diagnostic overlays during the resource measurement and read their counters at interval boundaries. Repeat an interval if a notification, large background task, or debugger attachment changes the conditions.

1. **Count work at its source.** Read `PetRenderView.sceneUpdateCount` and `viewRenderCallbackCount` before and after each interval. The first counts completed `SKScene.didFinishUpdate()` callbacks; the second counts render delegate *requests*, because that callback chooses whether to update/render and does not prove a GPU presentation occurred. Also record `PetWindowController.movementTickCount` to detect a window display link that continues after movement. The settled, paused, and hidden intervals should show no continuing callbacks after a small transition allowance; investigate any sustained increase. A paused SpriteKit view stops actions/physics, but that property alone is not a measured zero-render or zero-energy guarantee. [Pause behavior](https://developer.apple.com/documentation/spritekit/skview/ispaused), [render delegate](https://developer.apple.com/documentation/spritekit/skviewdelegate/view(_:shouldrenderattime:))
2. **CPU and memory.** Select Spriglet in Activity Monitor, record sampled CPU and memory for each interval, and record its Energy pane values. For repeatable command-line CPU samples, first determine the exact process ID, then use `top -pid <PID> -l 31 -s 2 -stats pid,command,cpu,mem,threads,time`; discard the first CPU sample and retain the raw output with timestamps. Use the same tool and units across comparisons. Activity Monitor Energy Impact is a relative indicator, not watts or projected battery lifetime. [CPU activity](https://support.apple.com/guide/activity-monitor/view-cpu-activity-actmntr43452/mac), [energy consumption](https://support.apple.com/guide/activity-monitor/view-energy-consumption-actmntr43697/mac)
3. **Find a continuing loop.** Launch the intended Release executable directly, attach CPU Profiler or Time Profiler to its exact PID, verify the captured target path, and inspect the settled/hidden interval. Use Allocations/Leaks for retained growth; use Metal System Trace or Game Performance when GPU submissions remain in question. A diagnostic callback count alone cannot establish the compositor/GPU's complete cost. Profile one concern at a time and note the profiler's own overhead. [Performance workflow](https://developer.apple.com/documentation/xcode/improving-your-app-s-performance), [Metal analysis](https://developer.apple.com/documentation/xcode/analyzing-the-performance-of-your-metal-app)
4. **Mark transitions without a new polling timer.** Record existing pause, hide, sleep, and resume boundaries with `OSSignposter`/`Logger` if needed. Avoid per-frame file writes or a high-frequency diagnostics refresh, which would contaminate an idle measurement. [OSSignposter](https://developer.apple.com/documentation/os/ossignposter)
5. **Check growth and sleep interference.** Compare settled memory after warm-up with settled memory after 100 show/hide/animation cycles and after a longer run. A temporary texture allocation is different from growth that persists after the app settles. Check Activity Monitor's Preventing Sleep column while static and animating. Document the observed baseline before setting a final memory or CPU budget.

These measurements inspect the app process and renderer; they require no desktop image capture or Screen Recording permission. Instruments may need macOS Developer Tools authorization for process profiling. Visual interaction checks can be done by a person without recording the display.

Do not use the new Power Profiler documentation as evidence that a macOS battery measurement was performed: Apple's current guide scopes capture to iPhone/iPad, despite the template appearing in Xcode's local template list. Likewise, Processor Trace capture requires supported hardware (currently M4 or later on Mac); CPU/Time Profiler remain available for other Macs. [Power Profiler scope](https://developer.apple.com/documentation/xcode/measuring-your-app-s-power-use-with-power-profiler), [Processor Trace requirements](https://developer.apple.com/documentation/xcode/analyzing-cpu-usage-with-processor-trace)

## Exit criteria and observation record

Phase 1 is complete when the desktop matrix's window/input/suspension rows have reproducible observations, static/hidden rendering stops continuing work, and measured CPU/memory/GPU behavior supports keeping this rendering approach. If precise character-boundary click-through or idle GPU use fails, record the failure and fix or change that mechanism before committing to the full animation library.

For every performed run, append: date, source revision or working-tree snapshot, build/OS/hardware, exact scenario and duration, raw trace/log path, observed values, pass/fail, and unresolved limitation.
